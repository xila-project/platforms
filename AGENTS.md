# Platforms development

Keep device interfaces and portable runtime contracts in Core; implement platform backends here. Preserve package names, runtime persistence and device permissions. Use `mise run test:seed`, `mise run build:native`, and `mise run check:browser` as applicable. Seed generation consumes separately built application artifacts through `XILA_APPLICATIONS_DIR`; do not assume applications are workspace members. Package checksum verification is not publisher authentication. Do not claim hardware, browser or Docker validation without running it on that target.

- When inspecting or improving the native graphical UI, use the Debug agent instead of relying on source inspection alone. Start `native_example` with `--display-driver headless` to work without X11 or Wayland (`--display-driver native` selects the windowed driver and remains the default). Headless mode starts the Debug transport in the background; then, as the same OS user, prefix these commands with `cargo run -p xila-drivers-native --bin xila-debug --`: `diagnostics`, `resolution`, `screenshot /tmp/xila-ui.png`, `ui-tree`, and `wait-for --text TEXT --timeout-ms 3000`. `wait-for` observes text in a bounded snapshot and reports timeout or truncation; it does not prove that the UI is idle. Use `pointer move X Y` followed by `pointer button press|release`, or `key NAME press|release` and `text TEXT`, to interact. The Debug application gets screen capture, UI state, and injected input through Xila graphics APIs; diagnostics use Xila task and memory APIs. Drivers supply output and physical inputs but are not queried or controlled by the Debug application. The client writes screenshot PNGs to the requested host path. JSON headers are capped at 64 KiB, screenshot payloads at 8 MiB, requests at 16 KiB, and printable ASCII text at 4096 bytes. The native control transport is available on Unix hosts only. See `examples/native/README.md` for the complete headless workflow.

# Optimization and Profiling

- For optimization requests, define the workload first and record a native baseline before editing hot paths. Use the same inputs, locale, disk state, resolution, network mode, duration and machine for the comparison. Build outside the measured interval and run `XILA_APPLICATIONS_DIR=/path/to/applications/target/wasm32-wasip1/release-wasm mise run image:native` to build guest applications and the LittleFS seed image first.
- Build an optimized binary with symbols using `mise run build:profiling -- --features prebuilt-applications` for OS workloads (the feature is compatibility-only; omit it for independent benchmarks). Applications load from the disk image, not from the recorder's `--applications-dir` (used only for artifact hashing). Record uninstrumented measurements with `cargo run --manifest-path tools/profiling/Cargo.toml -- measure --scenario NAME --output target/profiles/BASELINE --runs 3 --duration 30 --applications-dir /path/to/applications/target/wasm32-wasip1/release-wasm -- target/profiling/native_example --terminal --no-network --seed-image target/seed/native/seed.img`. Existing disks are not re-seeded automatically: restore the same disk fixture between runs. Read `summary.json` and per-run logs; a duration limit is a bounded observation, not successful workload completion. Do not use failed or forcibly killed runs to claim improvements.
- For attribution, rebuild with `mise run build:profiling -- --features profiling,heaptrack`. The `profiling` feature records task/spawner/thread identity, cumulative poll CPU time, poll/wait wall time and allocation request volume in each run's `runtime.json`. The `heaptrack` feature annotates the native custom allocator. Features are disabled by default and Linux-only instrumentation compiles out on other targets.
- Use the recorder's `cpu` mode with separately installed Samply (or `--tool perf`) and `heap` mode with heaptrack. Read the README's profiling section for artifacts and limitations. Keep external profiler overhead and feature-enabled counters out of uninstrumented before/after consumption comparisons.
- CPU time, elapsed latency, RSS, allocator-used/reserved bytes and allocation request volume are different metrics. Task IDs can be reused: use the manager/generation identity in reports. Executor poll CPU includes task CPU; do not add them together. Snapshots are periodic, not final or peak heap reports. Check active poll/wait flags: long-running polls do not update completed CPU/counts until they return. Native improvements need follow-up validation on the intended Wasm/embedded target.
